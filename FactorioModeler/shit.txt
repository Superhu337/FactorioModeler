public class ServiceLocator
{
    private static readonly Dictionary<Type, Func<object>> _services = new();

    public static void Register<TInterface>(Func<object> factory)
    {
        _services[typeof(TInterface)] = factory;
    }

    public static T Get<T>() where T : class
    {
        if (_services.TryGetValue(typeof(T), out var factory))
            return factory() as T;
        throw new KeyNotFoundException($"Service {typeof(T).Name} not registered");
    }
}

{

// Services/EventBusService.cs (НОВОЕ!)
public class EventBusService : IEventBus
{
    private readonly Dictionary<Type, List<Delegate>> _subscribers = new();

    public void Subscribe<TEvent>(Action<TEvent> handler) where TEvent : IEvent
    {
        var eventType = typeof(TEvent);
        if (!_subscribers.ContainsKey(eventType))
            _subscribers[eventType] = new List<Delegate>();
        
        _subscribers[eventType].Add(handler);
    }

    public void Publish<TEvent>(TEvent @event) where TEvent : IEvent
    {
        var eventType = typeof(TEvent);
        if (_subscribers.TryGetValue(eventType, out var handlers))
        {
            foreach (var handler in handlers)
                (handler as Action<TEvent>)?.Invoke(@event);
        }
    }
}

🎯 Что такое IEvent?

IEvent — это маркерный интерфейс (пустой интерфейс). Он нужен только чтобы пометить классы как "события".

Вот всё, что в нём есть:

csharp
public interface IEvent
{
}

Да, просто пустой интерфейс. Ничего больше.

🔍 Зачем он нужен?

Смотри, когда ты пишешь в EventBus:

csharp
public interface IEventBus
{
    void Subscribe<TEvent>(Action<TEvent> handler) where TEvent : IEvent;
    //                                                  ↑ ВОТ ЗДЕСЬ!
    void Publish<TEvent>(TEvent @event) where TEvent : IEvent;
}

Условие where TEvent : IEvent означает: “TEvent должен наследовать IEvent”

Это гарантирует, что ты можешь публиковать только события, которые реализуют IEvent.

📝 Пример
csharp
// ✅ ПРАВИЛЬНО - наследует IEvent
public class CardSelectedEvent : IEvent
{
    public string ItemName { get; set; }
}

// ❌ ОШИБКА - не наследует IEvent
public class RandomEvent
{
    public string Message { get; set; }
}

// Использование:
eventBus.Publish(new CardSelectedEvent { ItemName = "iron-plate" }); // ✅ ОК
eventBus.Publish(new RandomEvent { Message = "hello" }); // ❌ ОШИБКА КОМПИЛЯЦИИ

Назначение файлов и принцип работы
Главная идея

Сейчас окна знают друг о друге напрямую: SearchPopUp вызывает MainWindow.CreateRecipeCard, а MainWindow создаёт SearchPopUp. Поэтому любое новое окно требует правок в старых.

После рефакторинга компоненты общаются через посредников:

События (EventBus): «что-то произошло», отправитель не знает, кто слушает.
Интерфейсы сервисов: «мне нужна функция X», а кто её реализует, неважно.
WindowManager: единственное место, которое знает, как создавать и показывать окна.
Файлы по слоям
Models/
FactorioData.cs (уже есть). Только данные: рецепты, предметы, машины. Логики и ссылок на UI нет.
IEvent.cs. Пустой интерфейс-маркер. Нужен, чтобы EventBus принимал только классы, помеченные как события.
ConnectionInfo / BorderData. Это тоже данные: «что соединили» и «что лежит в иконке». Сейчас они лежат внутри CurveBuilder.cs и RecipeCard.xaml.cs. Вынеси их в Models, чтобы не было циклических зависимостей между Views и Scripts.
Services/
IEventBus + EventBusService. Хранит словарь «тип события → список подписчиков». Subscribe добавляет обработчик, Publish вызывает всех подписанных на этот тип. Это почтовое отделение: отправитель и получатель друг друга не знают.
ApplicationEvents.cs. Набор классов-событий: RecipeSpawnedEvent, ConnectionCreatedEvent, IngredientClickedEvent и т.д. Каждый несёт только данные о случившемся. Это контракт между частями программы.
IDataService + DataCollector. Сейчас DataCollector и запускает игру, и хранит данные, и ищет. Интерфейс оставляет окнам только то, что им нужно: GetRecipes(), GetRecipeIcon(). Окнам не нужно знать про запуск Factorio.
IWindowManager + WindowManagerService. Знает, как создать каждое окно, где его позиционировать и когда переиспользовать (твоя логика с Opacity для поиска переедет сюда). Окна просят: «покажи поиск», не зная, как он устроен.
ICardDataExtractor. Читает данные из карточек: названия предметов, количества, список всех иконок. Сейчас такая логика размазана по CurveBuilder и RecipeCard. Все новые функции «получить инфу из карточек» опираются на него.
Views/

Окна и контролы. Они делают три вещи: рисуют UI, ловят действия пользователя и публикуют события или вызывают сервисы. Бизнес-логики внутри быть не должно.

Scripts/

CurveBuilder, SearchFunc, PathExtensions. Утилиты без знания об окнах. CurveBuilder лучше не вызывает MainWindow, а возвращает результат или публикует событие.

App.xaml.cs

Composition root: единственное место, где создаются и связываются все сервисы. Здесь решается, какая реализация стоит за каждым интерфейсом.

Как это работает на примере

Пользователь выбирает рецепт в поиске:

SearchPopUp публикует RecipeSpawnedEvent и ничего не знает про MainWindow.
MainWindow подписан на это событие и создаёт карточку на холсте.
Если позже понадобится окно статистики, которое тоже реагирует на новые карточки, оно просто подписывается на то же событие. Старый код не меняется.
Как добавлять новый функционал
Новое окно
Создай XAML-окно. Зависимости (сервисы, шина) принимай через конструктор.
Добавь метод показа в IWindowManager и реализуй его в сервисе.
Зарегистрируй окно в App.xaml.cs.

MainWindow и остальные окна не меняются.

Новая функция «получить данные из карточек»
Реши, это запрос («дай мне суммарные входы всех карточек») или реакция («когда создана связь, пересчитай»).
Запрос оформи как новый интерфейс-сервис (например, ICardAnalyzer) с реализацией. Он работает с данными, а не с элементами WPF.
Реакцию оформи подпиской сервиса на существующие события.
Зарегистрируй в App.xaml.cs, подключи в нужном окне через конструктор.
Новое событие

Если нужно сообщить о чём-то новом (например, «карточка удалена»), добавь класс в ApplicationEvents.cs и публикуй его там, где это происходит. Подписчики добавляются независимо.

Правило для себя
Если окно А хочет что-то получить, оно идёт через сервис-интерфейс.
Если окно А хочет сообщить, что что-то произошло, оно публикует событие.
Если окно А хочет показать другое окно, оно идёт через IWindowManager.
Напрямую вызывать методы другого окна нельзя.
Подводные камни
Утечки подписок. Шина хранит ссылки на обработчики. Если карточку удалили с холста, но не отписали, она остаётся в памяти и продолжает реагировать. Поэтому в интерфейсе нужен Unsubscribe, и вызывать его надо при удалении карточки или закрытии окна.
Не превращай всё в события. Для прямых запросов («дай данные») события неудобны, там нужны сервисы. События только для «это произошло».
DI-контейнер необязателен. Microsoft.Extensions.DependencyInjection ставится через NuGet и работает на .NET Framework 4.8.1. Но для проекта такого размера можно сначала обойтись ручным созданием сервисов в App.xaml.cs и перейти на контейнер позже.
Порядок работ. Не переписывай всё сразу. Сначала IEvent + EventBus и перевод одного сценария (поиск → создание карточки), проверь, что работает, потом остальное. Так ошибки видны сразу, а не накапливаются.

Если захочешь, могу проверить твой код после каждого шага или объяснить любой из пунктов подробнее.
